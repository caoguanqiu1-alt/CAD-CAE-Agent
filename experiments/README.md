# 对照实验：批量计划与结果核验

本实验回答两个具体问题：**合并工具调用能减少多少接口耗时？把验收规则落实为校验工具，能发现哪些“返回成功但结果错误”的情况？** 2026-09-30 在 Windows 11 上实际运行；脚本、逐轮计时和全部故障输入均公开。

**范围：真实 MCP stdio 通信 + 仓库现有生产校验函数 + 人工构造的故障样本。没有调用 LLM、SOLIDWORKS COM 或有限元求解器。** 因此结果用于评估接口与流程，不是工程建模速度、真实任务成功率或“加载 Skill 后模型更聪明”的证明。

## 文件与复跑

| 文件 | 用途 |
| --- | --- |
| [agent_workflow_benchmark.py](agent_workflow_benchmark.py) | 自行启动最小 MCP 子进程，运行全部对照和断言；直接导入仓库源码。 |
| [results.json](results/2026-09-30/results.json) | 环境版本、源代码 SHA-256、40 轮原始计时、故障输入、校验明细及停止轨迹。 |
| [timings.csv](results/2026-09-30/timings.csv) | 逐轮、逐方案耗时，方便另行统计。 |

在仓库根目录、已安装项目依赖的 Python 3.13+ 环境中运行：

```powershell
& .\.venv\Scripts\python.exe experiments/agent_workflow_benchmark.py `
  --repetitions 40 --warmups 5 --nodes 12 `
  --output experiments/results/local-rerun
```

新结果写入 `local-rerun`，保留已发布数据。此命令不需要安装或启动 SOLIDWORKS，不读取个人模型，不创建 CAD 几何。停止轨迹实验只在系统临时目录创建空的路径检查文件，并在完成后清理。

当次环境为 Python **3.13.15**、FastMCP **4.0.10**、MCP Python SDK **2.2.0**、Pydantic **2.13.5**；源码基线 `35781348e56e3181d2d4736b3a2c5fc9fc765703`。新增脚本当时尚未提交，其 SHA-256 与生产源码哈希一并记录在 JSON 中，统一将 CRLF 换行规范为 LF 后计算。软件版本与机器负载会影响耗时；这些数值不代表项目最低依赖环境的速度。

## 对照一：12 次逐项校验与 1 次批量校验

### 设计

同一进程、同一条已初始化的 stdio 连接、相同的 `sw2020_validate_plan` 工具，校验 **12 个互不依赖的节点**。每个节点包含一个 100 × 60 × 10 mm 矩形凸台配方，以及不同的特征名与草图名；X 中心按 100 mm 递增，输入在脚本中固定生成。

- **逐项方案：** 将 12 个节点分别放进独立计划，顺序发送 12 次工具调用。
- **批量方案：** 将同样 12 个节点放进一个计划，发送 1 次调用。
- **直接 Python 参照：** 在客户端进程直接运行同一个 `ModelingPlan.model_validate → compile_plan`，用于观察协议、进程与序列化的额外成本。

独立计划会重复计划头和预期体积；合并计划包含汇总预期值。脚本逐轮断言两种 MCP 方案的 **编译后 groups 列表完全一致**。这里校验的是配方，不是在 CAD 中实际执行 12 个凸台；输入字节数也不是完整协议流量，更不是 LLM token 数。

预热 5 对后测量 40 对，每轮交换先后顺序，使用 `perf_counter_ns`。计时包含构造工具请求、stdio 往返、服务端验证、返回结果解析与 groups 提取；一致性断言在计时之后执行。无人工延时，不并发请求。P95 为排序后的第 `ceil(0.95 × n)` 项。

### 实测

| 方案 | MCP 调用 / 任务 | 中位耗时 ms | P95 ms |
| --- | ---: | ---: | ---: |
| 逐项 MCP 校验 | 12 | 16.55 | 20.05 |
| 批量 MCP 校验 | 1 | 1.97 | 2.46 |
| 直接 Python 批量编译参照 | 0 | 0.25 | 0.48 |

在此工作负载下，批量方案将调用数减少 **91.7%**，中位往返耗时减少 **88.1%**，两种中位数的比值为 **8.41**。比例按未四舍五入数据计算：`1 − 1.96855 / 16.5536`。输入计划 JSON 总字节数由 3,786 降至 2,500；完整 JSON-RPC 流量未测量。

最小服务的启动加初始化耗时为 **1,569.13 ms**，仅观察一次，单独记录，没有混入热连接计时，也不代表完整 149 工具服务的启动耗时。

**结论：收益来自减少重复往返与计划头开销。MCP 提供可发现、结构化的工具边界，本身也有传输成本；直接 Python 参照更快。** 不能将这里的 8.41 倍外推到真实 COM 建模、Simulation 求解、远程 HTTP 或包含 LLM 推理的完整任务。

## 对照二：输入和结果的故障注入

### A. 输入契约：不校验就转发，还是先编译计划

基线是一个明确的**不做输入检查、原样转发的脚本策略**。实验组将相同输入经真实 stdio 发送到生产 `sw2020_validate_plan`，检查 MCP 返回是否为错误。基线没有错误拦截能力，这是其定义；这个对照测量的是增加输入契约后的覆盖范围，不是在模拟某个裸 Agent 的判断能力。

| 注入错误 | 样本数 | 生产校验拒绝 |
| --- | ---: | ---: |
| 错误 schema / SW 年份 / 单位 / 未知字段 | 4 | 4 |
| 空节点 / 缺少独立预期指标 | 2 | 2 |
| 重复节点 ID / 重复特征名 | 2 | 2 |
| 缺失依赖 / 循环依赖 | 2 | 2 |
| 零拉伸深度 / 负矩形宽度 | 2 | 2 |
| **合计** | **12** | **12** |

两项正常对照均通过；其中乱序依赖被正确编译为 `node_0 → node_1`。未经校验的转发策略拦截 **0/12**，生产校验拦截 **12/12**。这是选定样本的检出计数，不是“真实输入错误率降低 100%”。

另外专门测了两项边界：**不存在的基准面名称**和**与配方不符但为正数的预期体积**均通过纯计划校验。前者须在真实文档中解析，后者须通过独立设计依据及执行后的几何回读发现。输入 schema 无法承担完整工程验收。

### B. 结果契约：只看 success，还是检查指标与特征

基线以 `status == success` 判断任务完成。实验组对同一组返回数据调用生产 `sw2020_compare_results`。所有上游返回均故意标记为 `success`，其中 8 个分别只改变以下一项：实体数、体积、表面积、质心、面数、边数、顶点数、特征类型。

参考指标为 1 实体、60,000 mm³、15,200 mm²、质心 (0,0,5) mm、6 面 / 12 边 / 8 顶点，特征类型为 `Extrusion`。另设两项正常对照：完全一致，以及体积/面积相差 0.005、质心 X 相差 0.0005 mm；后者在默认绝对容差内。

| 验收策略 | 检出错误结果 | 正常对照通过 |
| --- | ---: | ---: |
| 只看上游 success | 0 / 8 | 2 / 2 |
| 数值与特征类型核验 | 8 / 8 | 2 / 2 |

**结论：增加可计算的验收规则，能阻止这 8 类“成功但指标错误”的样本被当成完成。** 正常对照保留了容差，避免把允许的数值微差当成错误。

同时测了一个范围限制：只改变快照的文档标签、保留全部指标，比较器仍返回 `matched`，且 `live_verification=false`。调用方必须另行守住文档身份并获取实时快照；相同体积、面积和拓扑计数也不能证明 BREP、草图约束、尺寸关联或设计意图一致。

## 补充：异常时是否停止

直接运行生产 `run_simulation_plan`，用固定响应函数代替真实 COM 桥接。这个部分验证停止轨迹，没有旧流程速度对照，也没有实际创建研究或求解。

| 注入状态 | 实际调用轨迹 | 创建研究调用 | 自动重试 | 结果归档 |
| --- | --- | ---: | ---: | --- |
| 活动文档有未保存修改 | `check` 后停止 | 0 | 0 | 未创建 |
| 创建研究返回 unknown | `check → inspect_geometry → resolve_geometry → create_static_study` 后停止 | 1 | 0 | 未创建 |

第一种返回 `error / ACTIVE_DOCUMENT_NOT_CLEAN_COPY`，第二种返回 `partial / STEP_FAILED` 并要求检查现场。记录证明这些控制流在注入条件下生效；不能证明所有真实超时或崩溃都能安全恢复。

## Skill 和 MCP 分别贡献什么

**Skill 负责把经验写成可复用的操作与验收规范。** 例如要求先明确单位、从工程图取得独立预期、预检后执行、分别检查位移和应力收敛、遇到未知写入先查现场。它有助于让 Agent 一致地选择步骤，但指令是否被触发和遵守仍取决于具体 Agent。

**MCP 负责把能力和反馈变成可调用接口。** 本仓库在这些接口背后实现了 schema 校验、批量执行、文档守卫、状态回读、串行 COM 和持久请求 ID。错误拦截与重复执行保护由具体实现提供，不能仅归因于采用 MCP 标准。

两者结合的价值是：Skill 指导 Agent 调用正确的预检与验收工具，工具把部分规则变成可检查、可重复的约束。本实验量化了**批量调用与显式校验的收益**，没有独立测量 Skill 文件本身的因果增益。[OpenAI 的 Skill 评估方法](https://developers.openai.com/blog/eval-skills)也要求记录真实 Agent 轨迹并对完成结果和执行步骤评分；[MCP 官方 SDK 说明](https://ts.sdk.modelcontextprotocol.io/v2/)将其定位为连接 AI 应用与外部系统的开放标准。

若以后要测量 Skill 的独立作用，应固定模型版本、任务、工具和采样配置，只改变 Skill 是否加载；重复运行并公开轨迹，评分工程图关键尺寸、实体、保存重开、失败恢复、人工干预和 token/耗时。当前没有这组 LLM A/B 数据，故不填写 Agent 成功率或 token 节省率。

## 与真实 CAD / CAE 证据的关系

- 历史真实建模批量调用约 **5.077 s**、工具内部约 **4.259 s**，来自 2026-09-09 的[验收记录](../SW2020_WORKFLOW.md#actual-acceptance-2026-09-09)；未做同条件逐项对照，也未在本次重跑。
- 皮带轮、阀体、壳体和泵体已有[真实建模记录](../docs/modeling/showcase.md)，各自的简化与验证范围分别注明。
- 多网格静力与销轴接触有[真实 Simulation 数值](../docs/cae/verification.md)，不能从离线校验时延推算其求解速度或安全性。
- 本次另运行 **11 项建模计划 + 8 项仿真计划合同测试，19/19 通过**。这些测试验证相关接口和停止条件；没有运行全部上游测试或新的真实 CAD/CAE 求解。

读取数据时以原始 JSON/CSV 为准；报告只对展示值做四舍五入，不筛除计时样本。单机、40 对计时和有限的人工故障样本限制了结论范围。可复跑性支持核对这些具体收益，不能替代真实工程验收。
